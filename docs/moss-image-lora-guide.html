1先懂這顆模型

有六件事跟其他模型不一樣，照抄舊設定一定出錯。

① Base 不是 CFG 蒸餾模型

官方對 Base／SFT 的預設推論都是 CFG 3.0（範圍 3–6）。

設成 1.0 會變成單次 forward，連跳層指引都沒有，畫面會偏平；但 4 步蒸餾路線是例外，見 §8。

② 邊長是 16 的倍數

VAE 8× 下採樣再乘上 2×2 patch，有效 stride 16 px。

不是 32。dataset 解析度與寬高都受此限制。

③ 文字編碼器凍結

Qwen3.5-9B，走 chat template，上限 4096 token。

句子通常較貼近 chat template；tag 串也可行，內容比格式重要。

④ 負向分支跳過 block 22

這是 SLG（跳層指引），LoRA 預設也要排除 layers.22.。

目的是不破壞 CFG 的對比；放錯層級不會報錯，也不會生效。

⑤ 官方建議 Base；本專案走 SFT

ai-toolkit 預設「MOSS-Image SFT」；官方則把 Base 保留給社群訓 LoRA。

本專案四顆 LoRA 都在 SFT 上訓，因為部署棧是 SFT + 4 步蒸餾 LoRA。兩條路線不要混用；跨底模可移植性沒有 A/B。

⑥ 它收斂得慢

300 步就能認人，25–40 張的資料集到 1500–1600 步都還在進步。

所以不能只看最後一顆 checkpoint；每 100–250 步都要留，小資料集用 100。
最容易被抄錯的一格

上一顆模型（Qwen-Image-2.1）的預覽 guidance_scale 是 1.0，因為它是 CFG 蒸餾模型。 MOSS 的 30–50 步路線相反：3.0。把 1.0 搬過來，你會在完全沒有 CFG 的狀態下判斷 LoRA 好壞。

但如果你用 4 步蒸餾 LoRA 做部署預覽，CFG 要回到 1.0；兩者是不同的檢查，不要互相取代。

2資料集怎麼挑

張數是上限，多樣性才是變數。

張數：25–40 是保守區間；7–15 張可做，但要壓曝光

可查的人物案例是 56 張（1200 步、單卡約 65 分鐘）、工具商自述的 62 張與 53 張。 注意 56 張那個案例被不同報告重複引用，不能當成多個獨立證據。 25–40 是低信心的營運區間，不是實驗最佳值；重複的構圖與背景會被併進「這個人」的概念裡， 所以張數是上限，多樣性才是變數。 本專案另外有三個資料點：15 張（v1）與 12 張（jo_stillcrazy）都乾淨；7 張（leedahye）在 900 步可用、 1050 步出現半透明鬼影。所以低於 15 張不是不能做，而是曝光次數要壓在 100–130， 而且泛化會明顯受限。

取景比例：用覆蓋率檢查，不要照抄單一個案

這是唯一有公開逐張統計的人物案例。要注意的是它仍然有缺口——作者自評「朝左的角度太少，側臉只有 4 張」。 同一作者前一次用「以頭肩照為主」的資料集，結果訓練久了會把全身 prompt 拉回大頭照。 下表是覆蓋率檢查，不是實驗出來的最佳比例。

維度建議為什麼
取景特寫 20–25%、半身 35–40%、全身 30%、背面 ≤10%缺全身，構圖會被鎖在胸部以上
角度正面約 40%，左右 3/4 各約 20%，左右側面各 10–15%（至少各 3 張）最常見的缺口，補齊後側臉 prompt 才聽話
服裝至少 4 套，單套 ≤50%同一件衣服會被併進「這個人」
光源至少 4 種（室內暖光、窗光、戶外陰天、直射日光）膚色被拉平通常是光源樣本太單一
背景至少 5 種不同場景同一面牆會變成「這個人」的一部分

解析度與裁切

  • 不要自己裁切。loader 會自動分桶縮放，而且不會放大——原圖太小就是浪費。
  • 原圖長邊至少 1024 px，否則那張圖注定只能餵小 bucket，臉部細節會被抹掉。
  • square_crop 保持 false。設成 true 會關掉分桶、每張中央裁成正方形。
  • 面積以 1 MP 為目標（1024×1024、880×1168、832×1248 都在這個範圍）。
一定要剔除的照片 近重複（同一張換濾鏡）、模糊或壓縮痕跡重、多人合照、被遮住半張臉、臉太小（全身照裡只佔一小角）、 有浮水印或字幕、重美顏（皮膚已無紋理）、大量背影。

3Caption 怎麼寫

格式沒有共識；「不要寫死外觀」是社群慣例，不是官方證實。

社群慣例（非官方證實） 不要描述觸發詞已經代表的外觀。髮色、瞳色、臉型、身材、年齡，通常不要寫。 這是多個人物 LoRA 實作者收斂出的做法；官方 recaption 是通用標註指引，不是人物 LoRA 配方。 你要讓 LoRA 從圖片學這些，寫進 caption 等於用文字硬拉，會削弱「觸發詞→身分」的綁定。
要寫不要寫
場景（street、cafe、studio）長相（臉型、眼睛大小、鼻子）
服裝（white shirt、denim jacket）髮色、瞳色
光線（window light、backlit、overcast）身材、身高、體型
角度與取景（profile、full body、close-up）「beautiful」「attractive」這類評價詞
動作與表情（laughing、looking at camera）畫質詞（8k、masterpiece、best quality）

格式：句子或 tag 串都可，內容才是關鍵

MOSS 的官方文件同時接受自然語言、tag 串與 JSON layout，社群也確實有人用 tag 串成功。 它的文字編碼器是走對話模板的 Qwen3.5-9B，句子通常較貼近它訓練時看到的東西； 但 tag 串不是錯，兩派都有成品——不要只調格式，先確認內容有沒有寫對。 

mychar, a woman standing in a bright cafe, wearing a white knit sweater, soft window light from the left, three-quarter view, shallow depth of field, candid expression
  • 觸發詞放句首，而且每張都要有。ai-toolkit 找不到時會自動補到最前面，但自己寫清楚比較不會出意外。
  • 長度抓 25–60 個英文詞（約 35–80 tokens）就夠。官方預訓練語料的中位數大約 75 token，人物 caption 不需要長篇。
  • 用英文寫。模型看過的英文資料量最大。
  • 一張圖一個場景描述，不要把所有可能都寫進去。

4Job 參數設定

下面這份可以直接貼進 ai-toolkit 的 job 設定，改成你的路徑與觸發詞即可。

UI 預設有四個要確認的地方
  • resolution: [512, 768, 1024] — 清單會拆成三份資料集，固定步數下是三份各分到 1/3 更新。它是「多尺度＋速度」的取捨，不是錯；受控比較時才用單一 [1024]。
  • caption_dropout_rate: 0.05 — 通用防過擬合值；人物小資料集建議改 0。
  • 預設底模是 SFT；官方建議 Base，本專案則直接用 SFT（見 §1 ⑤）。
  • 存檔預設只保留 4 個 checkpoint；人物建議 6–8，短跑用 100 步／10 顆。
job: extension
config:
  name: moss_char_lora_v1        # 輸出資料夾與檔名；重訓請改這裡
  process:
    - type: diffusion_trainer
      training_folder: output
      device: cuda:0
      trigger_word: "mychar"

      network:
        type: lora
        linear: 32
        linear_alpha: 32
        network_kwargs:
          ignore_if_contains: ["layers.22."]   # 不訓 CFG 負向分支跳過的層

      save:
        dtype: bf16
        save_every: 250           # 長跑用；短跑（<2000 步）改 100
        max_step_saves_to_keep: 6      # UI 預設 4；人物建議 6–8；短跑改 10

      datasets:
        - folder_path: /workspace/dataset
          caption_ext: txt
          caption_dropout_rate: 0.0    # 人物小資料集建議 0
          buckets: true
          square_crop: false            # 不要開；會跳過分桶、可能放大
          resolution: [1024]             # 受控比較用；混合清單是速度取捨，不是錯
          cache_latents_to_disk: true

      train:
        batch_size: 1
        steps: 2500                    # 官方 Base 版；本專案 SFT 版 1050–3000（見下表）
        gradient_accumulation: 1
        train_unet: true
        train_text_encoder: false      # 架構內已硬凍結
        gradient_checkpointing: true
        noise_scheduler: flowmatch
        timestep_type: shift
        optimizer: adamw8bit
        lr: 0.0001
        lr_scheduler: constant
        dtype: bf16
        cache_text_embeddings: false # 預設 false；OOM 再試 true 並確認 loss
        unload_text_encoder: false   # 單開 true 會毀掉 caption 訓練

      model:
        name_or_path: OpenMOSS-Team/MOSS-Image-Base
        arch: moss_image
        quantize: true
        qtype: convrot8
        quantize_te: true
        qtype_te: convrot8
        low_vram: true
        layer_offloading: false        # 16GB 實測可關；OOM 再開
        model_kwargs:
          uncond_skip_layers: [22]      # 官方 SLG

      sample:
        sampler: flowmatch
        sample_every: 250           # 長跑用；短跑（<2000 步）改 100
        width: 1024                    # 16GB 實測 1024 訓練可行；取樣 OOM 再降
        height: 1024
        guidance_scale: 3.0            # 30–50 步路線；4 步蒸餾用 1.0
        sample_steps: 30               # 驗收時改 50
        seed: 42
        neg: ""

注意：真正決定 Base 還是 SFT 的是 name_or_path，不是 arch 的標籤。 arch 只用來挑 UI 預設，載入時標籤會被切掉。 另外 sample.sampler 寫了不生效，MOSS 管線實際用 Euler；真正要調的是 steps、CFG、shift。

本專案 SFT 版的差異（四顆 LoRA 實際設定）
欄位官方 Base 版本專案 SFT 版
name_or_path.../MOSS-Image-Base.../MOSS-Image-SFT
steps25001050–3000（依張數換算曝光）
save_every / keep250 / 6–8100 / 10（短跑才不會漏掉最佳 checkpoint）
resolution[1024]v1.1 用 [1024]；v1／jo／lee 用 [512,768,1024]
sample30 步、CFG 34 步、CFG 1 + inference_lora_path（部署閘門）

cache_text_embeddings 可以放 train 層（切換全部資料集）或 datasets[] 層（逐資料集）；本專案的 YAML 放在 dataset 層，兩者都合法。 v1.1 用 dataset 層 true，訓練正常；沒有 A/B。

本專案單次實測（非官方數據） RTX 5070 Ti 16GB、1024 桶、offload 關、gradient checkpointing 開：約 2.4 秒/步、峰值約 11GB。 3000 步純 1024 約 125 分鐘；[512,768,1024] 混合 3000 步約 82 分鐘（等於三份資料集輪流）。 768 桶約 1.4 秒/步；512 桶約 1.0 秒/步。原始 log 未留存，low_vram 未在紀錄中註明（YAML 沿用 UI 預設 true），數字是量級參考，不是保證。
OOM 時先分階段，不要亂開開關 載入 OOM → 確認量化與 low_vram；訓練 OOM → 降 dataset 解析度或開 layer_offloading； 取樣 OOM → 降 sample.width/height。cache_text_embeddings 是最後才試的未驗證選項（預設 false）。

另外：low_vram 和 layer_offloading 是兩個獨立開關。 前者是把模型載到 CPU，不是「自動分批」。

曝光次數＝步數 ÷ 張數（混合清單是總計，每個解析度各約 1/3）。本專案的經驗值：80 次偏弱、150–200 次較好； 7 張的小資料集超過約 130 次開始出現鬼影。這是單一專案觀察，不是通則。

時間估算（16GB 單次實測，非官方數據） 1024 桶 2.4 秒/步：2500 步約 100 分鐘、3000 步約 125 分鐘。768 桶 1.4 秒/步、512 桶 1.0 秒/步。 以上不含模型下載、快取、預覽與存檔。
LoRA 強度指標（本專案觀察） 3000 步版本 |B| = 2.52；1200 步版本 |B| = 1.56。 步數不足時 adapter 增量明顯較小，要追上得續訓。只有兩個資料點，只適合同一份設定的相對比較。
最容易誤判的一件事 預覽預設只跑 30 步，官方推論建議 ≥50 步。 用 30 步的圖去判斷「這顆 LoRA 不夠好」，會低估它。驗收時一定要用 50 步重跑同一組 seed。

7訓練後怎麼驗收

用固定的三路對照＋4 步部署閘門，一次只改一個變數。

  1. 原模型（不套 LoRA）跑同一組 prompt — 這是 baseline，用來扣掉模型本身的審美傾向。
  2. 套 LoRA、不寫觸發詞 — 檢查有沒有概念外洩。
  3. 套 LoRA、寫觸發詞 — 這才是你實際會用的情境。
# 1 基本盤（與訓練集相似）
mychar, close-up portrait, front view, neutral expression, plain grey background

# 2 泛化（訓練集沒有的視角）
mychar, low-angle shot looking up, sitting on a staircase, harsh midday sun

# 3 換裝（caption 有標的屬性）
mychar, full body, wearing a red knit sweater and jeans, city street at dusk

# 4 側臉（訓練集的弱項）
mychar, side profile facing left, window light

# 5 外洩（不寫觸發詞）
a young woman standing in a greenhouse, fashion portrait, soft light

# 6 污染（完全無關）
a horse galloping across a field at sunset
驗收項目怎麼看
相似度正面、側面、四分之三角度各一張；與本人照片並排
體態全身照對照肩寬、腰線、髖寬、腿長比例——注意模型本身就會把人修得好看一些
泛化測一組訓練集沒有的構圖（例如資料集全是室內，就測戶外全身）
文字能力畫面裡放一段文字，看有沒有糊掉或拼錯
外洩第 2 路若也像本人，就是外洩
第四路：4 步部署閘門（本專案必做） 上面三路是 50 步、CFG 3 的品質驗收。實際部署是 4 步蒸餾 LoRA + CFG 1.0， 所以要再加一條：同一組 prompt、同一 seed，接 4 步蒸餾 LoRA 跑 4 步。 leedahye 的鬼影只有在這條路看得到；50 步 CFG 3 可能完全正常。

選 checkpoint 的方式：短跑用 100 步、長跑用 250 步間隔，把每一顆都跑同一組 prompt、同一個 seed， 挑「相似度夠、又還沒開始僵化」的那一顆。不要直接拿最後一顆。 leedahye 的最佳版本是 900 步，但 250 步間隔只會留下 1000 步與最終版，根本撿不到 900——這是為什麼小資料集要用 100。

8常見問題

訓練到一半 OOM，但看不出是哪一階段

載入、訓練、取樣三個階段的峰值不同，要分開處理：

  • 載入時 → 開量化 + low_vram
  • 訓練時 → 降 dataset 解析度（僅在 OOM 時；例如 1024 → 768）
  • 取樣時 → 降 sample.width/height，不必動 dataset
同一份設定再跑一次，馬上就結束了

它會從 output/<name>/ 最新的 checkpoint 續訓。改 config.name，或把舊輸出目錄搬走。

LoRA 在 ComfyUI 裡完全沒效果，console 一直印 lora key not loaded

舊版 ComfyUI（0.42.5）的 MOSS 分支只認 diffusion_model. 前綴的 key。 更新到 master 即可（PR #17296 已修）。ai-toolkit 產出的檔案本來就帶前綴，不受影響。

為什麼不能用 Turbo / DMD 版本當預覽基準？

那是蒸餾過的另一條路線，步數與 CFG 都不同（4–8 步、CFG 1）。用它看到的畫面， 不能用來判斷訓練中的 LoRA 進步了沒有；訓練中的預覽仍用未蒸餾模型、30 步、CFG 3。

但部署前一定要跑一次 4 步蒸餾。它不是「預覽基準」，而是「部署閘門」： 品質驗收看 50 步 CFG3，能不能用看 4 步 CFG1。兩者都過才上傳。

訓練完的 LoRA 要放哪一顆底模出圖？

官方路線：在 Base 上訓、在 SFT 上出圖，這是社群常見做法；但官方 USERGUIDE 沒有這樣說， 本專案也沒有 Base→SFT 的 A/B，所以標成「未驗證」。

本專案路線：直接在 SFT 上訓、在 SFT 上出圖，四顆 LoRA 都這樣做， 而且部署棧是 SFT + 4 步蒸餾 LoRA，不需要跨底模。若你要跟本專案一致，就用 SFT。

為什麼我的圖有淡淡的垂直條紋？

那是 SFT 模型本身的特性，不是你的訓練造成的。可以在推論端疊 DeBand LoRA，或直接用 Base。

16GB 真的能跑 1024 嗎？

本專案在 RTX 5070 Ti 16GB 上實測可以：1024 桶、offload 關、gradient checkpointing 開，約 2.4 秒/步、峰值約 11GB。 這是單次實測，非官方數據，不是所有 16GB 卡的保證。若 OOM，先確認量化與 low_vram， 再降 dataset 解析度或開 layer_offloading；取樣 OOM 則先降 sample.width/height。

checkpoint 只留 4 個嗎？

ai-toolkit 的 UI 新 job 預設是 4；手寫 YAML 完全不填時，核心 SaveConfig 預設是 5。 人物訓練建議調高到 6–8，因為最好的 checkpoint 不一定是最後一顆。留 6 顆等於只保留最後 6 顆（2500 步時是 1250–2500）， 更早的會被覆蓋；要回頭撿早期就設 8，或手動把想要的複製到別處。

短跑（<2000 步）請用 save_every: 100、max_step_saves_to_keep: 10。 1050 步、250 步間隔只會留下 250/500/750/1000/1050；本專案 leedahye 的最佳版本是 900 步，根本不會存在。

為什麼 YAML 的 cache_text_embeddings 是 false？

ai-toolkit 的預設就是 false；本專案 v1.1 曾在 datasets[] 層開 true， 1200 步訓練與取樣正常，但沒有 A/B，不能證明加速或等價。 只有在實際 OOM、且你願意檢查 loss 與輸出時才試 true。不要為了省 VRAM 先動一個沒驗過的東西。

訓完的 LoRA 怎麼合併成單檔？4 步預覽怎麼做？

本專案有兩支工具：scripts/merge_moss_lora.py 把人物 LoRA 併進 bf16 transformer， 公式是 W += cat(B_q, B_k, B_v) @ A，fp32 計算、bf16 寫回；已實測載入合併檔角色一致。 4 步預覽則用 scripts/patch_moss_inference_lora.py 加上 forward hook，設定 sample_steps: 4、guidance_scale: 1.0。這是看最終推論設定的樣子，不是訓練中的 checkpoint 比較； 訓練中的預覽仍用未蒸餾模型 30 步，驗收用 50 步 CFG 3，部署前再過一次 4 步 CFG 1；兩者都過才上傳。
